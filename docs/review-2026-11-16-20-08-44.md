# Database Implementation Review & Architecture Proposals

**Review Timestamp:** 2026-11-16 20:08:44 +01:00  
**Scope:** Database implementation, synchronization lifecycle, schema contracts, write admission, and query performance in `utmelab-api`.

---

## 1. Executive Summary

This review analyzes the storage and database layer in `utmelab-api`. The system uses an embedded SQLite replica managed through Turso libSQL (`turso` v0.8 with `sync` and `mimalloc`). The architecture decouples pipeline-owned content tables from API-owned platform tables. It provides load shedding via a non-blocking gate, long-poll synchronization with idle sleep, and strict schema shape assertions.

The core concurrency and replication mechanics are well engineered. However, this review identifies concrete technical debt in the textbook and query modules. These issues include missing indexes on high-traffic foreign keys, unbounded table scans on textbook endpoints, in-memory filtering of database rows, and unbatched chapter ingestion.

Below are the detailed observations, code-level findings, and prioritized proposals.

## 2. Storage Architecture & Baseline Review

### A. Concurrency and Gate Control (`src/store/mod.rs`)
* **Connection Pool:** [`ConnPool`](file:///home/kristency/Projects/utmelab-api/src/store/mod.rs#L41-L96) pre-warms connections at boot up to the gate capacity. In Turso's architecture, opening a connection dispatches work to the single sync IO thread. By recycling connections locally, read queries run on the local file without queuing behind network replication.
* **Non-Blocking Gate (`DbGate`):** The gate uses a tokio semaphore. When saturated, [`gate(s)`](file:///home/kristency/Projects/utmelab-api/src/store/mod.rs#L98-L105) rejects requests immediately with `AppError::DbSaturated` (HTTP 503) instead of accumulating an unbounded in-memory task queue.
* **Permit Release on Backoff:** During lock contention (`SQLITE_BUSY`), [`with_conn`](file:///home/kristency/Projects/utmelab-api/src/store/mod.rs#L165-L190) drops the gate permit and yields the pooled connection before sleeping on backoff. This prevents waiting tasks from starving active workers.

### B. Replication Lifecycle (`src/store/sync.rs`, `src/store/sync/`)
* **Long-Polling:** Steady-state pulls use long-polling via `with_long_poll_timeout`. The remote connection waits for database changes or a server-side timeout rather than generating constant poll traffic.
* **Idle Sleep:** If no HTTP requests arrive for five minutes, the sync loop enters idle sleep. The first request after sleep executes [`wake_if_sleeping`](file:///home/kristency/Projects/utmelab-api/src/store/sync.rs#L828-L878) under a write lock, ensuring concurrent queries share a single catch-up pull.
* **Replica Quarantine:** [`quarantine_replica`](file:///home/kristency/Projects/utmelab-api/src/store/sync.rs#L92-L114) inspects the SQLite magic header and engine error classes. Corrupted files are preserved with a `.corrupt-<timestamp>-<pid>` suffix before triggering a fresh remote rebuild.

### C. Write Safety & Admission (`src/store/write.rs`)
* **Admission Bounds:** Writes must pass [`ensure_write_admitted`](file:///home/kristency/Projects/utmelab-api/src/store/write.rs#L26-L46). If local unpushed operations exceed 256 or unpushed bytes exceed 64 MiB (e.g. during a prolonged upstream network failure), writes fail with `AppError::DbSaturated`.
* **Verification:** Local mutations run `SELECT changes()` on the same connection in [`execute_and_verify`](file:///home/kristency/Projects/utmelab-api/src/store/write.rs#L271-L290) to confirm expected row modifications.

### D. Shape Enforcement (`src/store/schema.rs`)
* **Dual Contracts:** The system tracks `CONTRACT_VERSION = 1` for content-bank tables and `API_SCHEMA_VERSION = 10` for platform tables.
* **Fail-Closed Inspection:** [`check_contract`](file:///home/kristency/Projects/utmelab-api/src/store/schema.rs#L664-L710) checks `PRAGMA table_info` for all 27 tables and asserted columns on boot and after change-bearing pulls. If any expected column is missing, data routes fail closed.

## 3. Findings & Technical Debt

### Finding 1: Missing Foreign Key Indexes on Textbook Tables
* **Location:** [`src/store/schema.rs` (Migration 9 & 10)](file:///home/kristency/Projects/utmelab-api/src/store/schema.rs#L540-L614)
* **Problem:**
  - `chapter_exercises` has an index on `(section_id, tier)`, but lacks an index on `chapter_id`.
  - `exam_traps` has an index on `(exam, subject)`, but lacks an index on `chapter_id` and `section_id`.
  - `exam_recall_checks` has an index on `(exam, subject)`, but lacks an index on `chapter_id` and `section_id`.
* **Impact:**
  [`get_chapter`](file:///home/kristency/Projects/utmelab-api/src/store/chapters.rs#L478-L514) queries all three tables by `WHERE chapter_id = ?1`. Because no index covers `chapter_id`, SQLite performs three full table scans per chapter request. When updating or deleting chapters in [`import_chapter`](file:///home/kristency/Projects/utmelab-api/src/store/chapters.rs#L131-L143), `DELETE FROM {table} WHERE chapter_id = ?1` also triggers full table scans.
* **Severity:** High

### Finding 2: In-Memory Filtering in `get_book`
* **Location:** [`src/store/chapters.rs#L388-L401`](file:///home/kristency/Projects/utmelab-api/src/store/chapters.rs#L388-L401)
* **Problem:**
  ```rust
  pub async fn get_book(s: &DbState, book_id: &str) -> Result<Option<(Book, Vec<ChapterSummary>)>, AppError> {
      let Some(book) = list_books(s)
          .await?
          .into_iter()
          .find(|book| book.id == book_id)
      else {
          return Ok(None);
      };
      let chapters = list_chapters(s, book_id).await?;
      Ok(Some((book, chapters)))
  }
  ```
  `list_books(s)` runs `SELECT ... FROM books ORDER BY title`, deserializes JSON fields (`parts`, `sources`) for all books in the database, and scans them linearly in Rust memory using `.find()`.
* **Impact:**
  Violates the bounded-memory and query discipline guardrail. It loads unneeded records and increases CPU allocation on request paths.
* **Severity:** Medium

### Finding 3: Unbounded Selection on Traps and Practice Endpoints
* **Location:** [`src/store/chapters.rs#L782-L830`](file:///home/kristency/Projects/utmelab-api/src/store/chapters.rs#L782-L830) and [`src/api/v1/textbooks.rs#L205, L240`](file:///home/kristency/Projects/utmelab-api/src/api/v1/textbooks.rs#L205)
* **Problem:**
  `list_traps` and `list_recall_checks` construct queries with `WHERE 1 = 1` and append optional filters for `exam` and `section_id`. If a client calls `GET /v1/textbooks/exam-traps` or `GET /v1/textbooks/exam-practice` without query parameters, the query runs without a `LIMIT` clause.
* **Impact:**
  The server retrieves, deserializes, and allocates every trap or practice item in the entire database, causing latency spikes and unbounded payload responses.
* **Severity:** High

### Finding 4: Serialized, Non-Transactional Chapter Ingestion
* **Location:** [`src/store/chapters.rs#L88-L158`](file:///home/kristency/Projects/utmelab-api/src/store/chapters.rs#L88-L158)
* **Problem:**
  `import_chapter` calls [`execute_write_local`](file:///home/kristency/Projects/utmelab-api/src/store/write.rs#L241-L269) individually for the chapter row, followed by 4 separate `DELETE` statements, and repeated individual calls for every section, exercise, trap, and recall check.
* **Impact:**
  Every call to `execute_write_local` acquires the write mutex, verifies row visibility, increments unpushed operation counts, and attempts an immediate network push. An import of a single chapter with 15 sections and 60 exercises executes over 80 independent write locks and push operations. If any statement fails mid-import, the operation leaves partial state because statements are not executed inside a single transaction.
* **Severity:** High

### Finding 5: Incomplete Index Inventory in `INDEXES` Constant
* **Location:** [`src/store/schema.rs#L52-L63`](file:///home/kristency/Projects/utmelab-api/src/store/schema.rs#L52-L63)
* **Problem:**
  `INDEXES` only lists indexes for `api_keys`, `api_access_tokens`, `topic_notes`, and `theory_questions`. The indexes added in Migrations 9 and 10 (`idx_chapters_book`, `idx_chapter_sections_chapter`, `idx_chapter_exercises_section`, `idx_exam_traps_exam`, `idx_exam_recall_checks_exam`) were never added to `INDEXES`.
* **Impact:**
  Creates divergence between initial schema definitions and migration scripts. If migrations are bypassed or altered during automated testing fixtures, those indexes are omitted.
* **Severity:** Low

## 4. Proposals & Actionable Recommendations

### Proposal 1: Add Migration 11 for Missing Textbook Indexes
**Objective:** Eliminate full table scans on chapter lookups and cascading deletions.

**Implementation Plan:**
1. Bump `API_SCHEMA_VERSION` from 10 to 11 in [`src/store/schema.rs`](file:///home/kristency/Projects/utmelab-api/src/store/schema.rs#L28).
2. Append version 11 to `MIGRATIONS`.
3. Apply the following index definitions:
```sql
CREATE INDEX IF NOT EXISTS idx_chapter_exercises_chapter ON chapter_exercises (chapter_id);
CREATE INDEX IF NOT EXISTS idx_exam_traps_chapter ON exam_traps (chapter_id, section_id);
CREATE INDEX IF NOT EXISTS idx_exam_recall_checks_chapter ON exam_recall_checks (chapter_id, section_id);
```
4. Add these indexes to the `INDEXES` constant for fresh database initializations.

### Proposal 2: Direct Single-Row Lookup in `get_book`
**Objective:** Replace in-memory array filtering with direct SQL point queries.

**Implementation Plan:**
In [`src/store/chapters.rs`](file:///home/kristency/Projects/utmelab-api/src/store/chapters.rs#L388):
```rust
pub async fn get_book(
    s: &DbState,
    book_id: &str,
) -> Result<Option<(Book, Vec<ChapterSummary>)>, AppError> {
    let rows = super::catalog::rows(
        s,
        "SELECT id, title, subject_area, level, edition, description, parts, sources \
         FROM books WHERE id = ?1 LIMIT 1",
        vec![turso::Value::Text(book_id.to_string())],
    )
    .await?;

    let Some(row) = rows.into_iter().next() else {
        return Ok(None);
    };

    let book = map_book(&row)?;
    let chapters = list_chapters(s, book_id).await?;
    Ok(Some((book, chapters)))
}
```

**Objective:** Enforce SQL pagination and prevent unbounded collection retrieval.

**Implementation Plan:**

### Proposal 4: Atomic Chapter Batch Import
**Objective:** Eliminate multi-push overhead and ensure atomic all-or-nothing chapter ingestion.

**Implementation Plan:**
Refactor `import_chapter` in [`src/store/chapters.rs`](file:///home/kristency/Projects/utmelab-api/src/store/chapters.rs#L88) to accumulate SQL statement tuples into a `Vec<(&str, Vec<turso::Value>)>` and invoke [`execute_write_batch`](file:///home/kristency/Projects/utmelab-api/src/store/write.rs#L132-L190):

```rust
let mut statements = Vec::new();

// 1. Chapter statement
statements.push((
    "INSERT INTO chapters ... ON CONFLICT(chapter_id) DO UPDATE ...",
    chapter_params,
));

// 2. Child deletions
for table in ["chapter_sections", "chapter_exercises", "exam_traps", "exam_recall_checks"] {
    statements.push((
        format!("DELETE FROM {table} WHERE chapter_id = ?1").leak(),
        vec![turso::Value::Text(chapter.chapter_id.clone())],
    ));
}

// 3. Collect child rows (sections, exercises, traps, checks)
for section in &chapter.sections {
    statements.push((INSERT_SECTION_SQL, build_section_params(chapter_id, section)?));
}
for exercise in &chapter.exercises {
    statements.push((INSERT_EXERCISE_SQL, build_exercise_params(chapter_id, exercise)?));
}
for trap in &chapter.exam_traps {
    statements.push((INSERT_TRAP_SQL, build_trap_params(chapter_id, trap)?));
}
for check in &chapter.exam_recall_checks {
    statements.push((INSERT_CHECK_SQL, build_check_params(chapter_id, check)?));
}

// Execute in a single SQLite transaction with one push notification
super::write::execute_write_batch(s, statements).await?;
```
